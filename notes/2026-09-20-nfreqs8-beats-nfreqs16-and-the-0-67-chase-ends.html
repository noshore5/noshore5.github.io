nfreqs=8 beats nfreqs=16 on every metric, and the chase back to 0.67 ends

2026-09-20 · ablation, complex-native dense-edge, temporal_graph_mamba

temporal_graph_mamba had just gotten its first verified full 6-fold run at nfreqs=16 after nearly a dozen failed spot-GPU attempts, so the obvious next question was whether that frequency resolution was actually buying anything. The same complex-native 2-channel [re, im] edge representation, same --precompute-chunk-size 2, same dense-edge GPU cache, run again with --nfreqs 8 instead of 16 — isolating the frequency-resolution axis from the significance-channel-drop axis that had been muddying comparisons all week.

Halving the frequency resolution wins outright

Six folds, same instance (g5.xlarge), same everything else. nfreqs=8 didn't just tie nfreqs=16 — it won on every metric that was measured:

metricnfreqs=16nfreqs=8
accuracy0.88270.9096
precision0.38730.4674
recall0.77780.7800
f10.40880.5028
average precision (AP)0.48360.5831
roc_auc0.94310.9610
epoch time3.46s2.81s
event-level hit rate (smoothed)5/66/6

That's the opposite of what "more frequency resolution should help" predicts, and it's not a cache-starvation artifact — both configs hit 100% dense-edge cache reuse during training. It's a real accuracy difference between resolutions, and nfreqs=8 is also cheaper to run.

Working hypothesis: nfreqs=16 overfits

The same fold (1_26), final epoch, told a consistent story on both sides:

nfreqs=16nfreqs=8
train loss0.11950.1539
val loss0.2349 (~2× train)0.0768 (< train)
train roc_auc0.99050.9844
val roc_auc0.9838 (< train)0.9857 (> train)

nfreqs=16's val loss nearly doubling its train loss, with val ROC-AUC trailing train, is a classic overfitting signature; nfreqs=8's val metrics matching or beating train look like a healthy fit instead. The mechanism is direct: the dense-edge tensor is [channels, E, T, F] with F = nfreqs, feeding straight into temporal_edge_proj and the complex projection, so doubling F doubles that layer's input width and parameter count against the same small LOSO training set — tens of positive preictal windows per fold. And it buys no new real information: same 8–40 Hz band, just sliced finer, with the finer bins individually noisier. It's the same pattern this repo keeps running into (NEGATIVES.md): added capacity on this dataset size tends to wash or hurt rather than help.

Caveat: this overfitting comparison is a single fold, not the full 6-fold aggregate train/val curves — worth confirming the same gap holds across all six before treating it as settled, though the aggregate AP already points the same direction.

Stop chasing 0.67

This result also closes out a question that had been open since drop_significance was removed: the historical 0.644–0.674 AP came from the old 4-channel dense-edge stack ([coh, sinφ, cosφ, significance]), and significance turned out to be a deterministic affine rescale of coh, not a real independent test — correctness grounds for removing it permanently, regardless of the accuracy cost. A dedicated --temporal-graph-edge-coh-affine-rescale flag was built to try to recover that ~0.10 AP under complex_native without reintroducing the correctness problem, but measured at both nfreqs=16 (0.484→0.491) and nfreqs=8 (0.583→0.583) it recovers essentially nothing. With nfreqs=8 now the clear best config on its own merits, the call is to accept AP ≈ 0.58 as the real current best and stop chasing 0.67 — the honest number for this representation, not a regression to explain away.

Put together: nfreqs=8 is a strict upgrade over nfreqs=16 — better on every metric, cheaper to run, and better-behaved on train/val gap — and the affine-rescale detour that was supposed to close the gap back to 0.67 is confirmed dead. temporal_graph_mamba's current best is nfreqs=8, no affine rescale, AP ≈ 0.58, and nobody should re-derive this comparison without a new idea.
