A torch-native CWT module, and a real GPU benchmark

2026-08-20 · performance, wavelet coherence, GPU

The wavelet transform underneath every coherence computation in this project has always run through fcwt, an FFTW-backed C++ library called from a plain, unbatched Python loop — one (sample, channel) pair at a time, CPU-only, no GPU involvement at all. This session started a plan to replace it with a torch-native (torch.fft) implementation: a correctness-preserving swap, not a redesign, aimed at eventually running the same computation on a GPU. Steps 0–5 of that plan are done and validated here; the actual pipeline swap (step 6) hasn't happened yet.

Building the module, and two real calibration bugs

The new module (utils/torch_cwt.py) computes the CWT via the Fourier convolution theorem — FFT the signal once, multiply against a precomputed frequency-domain Morlet filter bank, inverse-FFT back. Two real bugs turned up while calibrating against actual fcwt output rather than trusting the math in isolation: fcwt's frequency array runs high-to-low, the opposite of the natural construction order, which silently compared the wrong frequency's column against the wrong column until caught (magnitude correlation was ~0.22 until fixed, ~1.0 after); and the filter's peak amplitude needed an empirically-calibrated flat constant across scale, since a literal derivation gives an amplitude that wrongly grows at low frequency. That second bug alone accounted for a worst-case coefficient error of ~53 inside the region that actually reaches the model — high per-frequency correlation had been masking it, since correlation doesn't catch a systematic amplitude bias.

Parity validation

Magnitude and phase correlation between the new module and real fcwt output on actual CHB-MIT trials, restricted to the cone-of-influence region that's the only part that ever reaches the model: 0.999950–0.999962 magnitude Pearson r. A broader sweep across 60 trials, every channel, put the per-trial minimum at 0.99989 — every trial cleared the >0.999 bar. A stress test at 500 log-spaced scales on a real 300-second signal held the same correctness (median relative error 0.005%, no NaN/Inf across 38 million valid samples) — if anything tighter at high scale density than at the small canonical config.

The real GPU benchmark

Local Mac testing (CPU and Apple's MPS backend) gave a mixed, confusing picture — the naive torch implementation sometimes lost to fcwt's own algorithmic edge on long signals. That story didn't hold up on real hardware. A Runpod GPU pod (RTX 4090, ~8 minutes of uptime, about five cents) gave a clean answer instead:

Correctness held throughout the sweep — magnitude/phase correlation 0.999998–1.000000, no NaN or Inf at any size tested. The speedup grows with problem size rather than staying flat, which matters here specifically because the project's direction is toward longer windows and higher frequency resolution, not away from it — the win compounds with where this is headed rather than fading as the workload changes.

Not yet true, and worth being precise about: this is a validated preview of the ceiling, not a measured improvement to the real training pipeline. The classifier's actual feature-preparation code still calls fcwt; the torch-native module lives on a separate branch, one commit, wired into nothing yet. The benchmark above used synthetic signals shaped to match real data, not an end-to-end run of the actual model.

Open items

The actual swap — pointing the classifier's feature preparation at the new module and re-running the canonical evaluation to confirm scores don't move — hasn't started. The canonical config used for most of this session's validation (4s windows) is already outdated; the real target is 30s windows now, with a multi-hour continuous option to keep open, and the GPU benchmark above already covers that config directly. A visual demo script and its output image exist but aren't committed yet, and removing fcwt as a dependency entirely is explicitly deferred until after the real swap is confirmed clean.
